# Storix — design document (MVP)

> Name: **Storix** (the original spec used the provisional name "Clique"). Date: 2026-11-07. Status: **validated by Tristan on 2026-11-07**.
> Reference mockup (direction A "Nuit holo"): https://claude.ai/artifact/MPhGpyFMxAxszGaNKMDYGj
> Production URL: `https://storix.tristanhourtoulle.fr` (Railway custom domain).
>
> English translation of the original French spec. Values, structure and decisions are unchanged; only the product name was updated.

## 1. Intent

A private PWA where friends join a **league**, turn their phone photos into **collectible cards**, and fight over them through **boosters**. Direct inspiration: WikiMasters (Wikipedia articles → cards, rarity based on page views). Here the raw material is the group's memories: a card's value comes from the photo and its story among friends.

Success: the group opens the app every day for its boosters, adds photos spontaneously, and talks about the Legendaries they pulled. The app must be **spotless** (code and UX), **fast** (instant images, offline for the collection), hosted on **Railway**.

## 2. Goals, non-goals, anti-goals

**MVP goals**
1. Accounts, leagues, invitations by link.
2. Multi-photo upload → cards (title, tagged people), server-side image processing.
3. Automatically computed rarity + admin override, evolving over time.
4. Timed boosters with a stock, animated opening with a rarity glow before the flip, bad-luck protection (pity).
5. Collection, card detail (holo effect that follows device tilt), reactions.
6. Duplicates → dust; dust → craft a card or upgrade a copy to foil.
7. "Photo by" and "discovered by" credits.

**Non-goals (later, explicitly postponed by Tristan)**
- Wonder Pick (picking from a friend's booster).
- **Any exchange between members** (even simple), as well as the wanted-cards list and alerts (Tristan's decision).
- Quiz duels, themed sets and seasons with completion percentage.
- Push notifications, card image sharing (OG/PNG), automatic AI moderation.
- Limited prints / serial numbers: **copies are unlimited** (Tristan's decision).

**Anti-goals (failure even if "it works")**
- Any payment or real-money mechanic.
- Personal data leaks: exposed GPS/EXIF, images reachable through a guessable public URL.
- A slow app: a stuttering grid, images that reload on every visit.
- Dirty code: `any`, business logic in routes, no tests on pulls and rarity.

## 3. Constraints (decided by Tristan)

- **Stack**: Vite SPA + Fastify (separate API), **always the latest versions** at install time, **TypeScript everywhere** (strict), **Tailwind** for CSS. Code in English, clean code first.
- **Auth**: **no email at all** in the app (no sending address). Username + password, **passkey offered after the first login**. Forgotten password = **single-use reset code generated by a league admin**, handed over manually.
- **Hosting**: Railway. **Railway Bucket** (private) + **signed URLs** + aggressive caching.
- **Scale**: 5 to 30 people per league, a few leagues. No scaling need.
- **Design**: direction A "Nuit holo" (very dark background `#0A0A10`, surfaces `#15151E`, text `#F2F2F7`, violet accent `#A78BFA`, cyan `#22D3EE`, Space Grotesk for headings, Inter for body text). Rarity colors: Common `#A1A1AA`, Uncommon `#4ADE80`, Rare `#60A5FA`, Epic `#C084FC`, Legendary `#FBBF24`, Mythic = rainbow holo.
- **Process**: no Linear task for this project. No commit without an explicit request.

npm versions noted on 2026-11-07 (to re-check at install): vite 8.3, react 19.3, @tanstack/react-router 1.170, @tanstack/react-query 5.107, @tanstack/react-virtual 3.14, fastify 5.12, drizzle-orm 0.45, better-auth 1.7, pg-boss 12.38, sharp 0.35, zod 4.6, tailwindcss 4.3, motion 14.10, @serwist/vite 9.5, typescript 7.0, @aws-sdk/client-s3 v3, thumbhash.

## 4. The product, screen by screen (MVP)

Bottom navigation: Home · Collection · (+) Add · Exchanges (greyed out "soon") · Profile.

1. **League home**: league name, dust balance, "booster ready" card (stock as pips, countdown to the next one, Open button), pity bar ("Epic guaranteed in N boosters"), members' recent reveals, short activity feed.
2. **Booster opening**: 5 face-down cards. Each back **glows in its rarity color** before being flipped. Reveal one by one (or "reveal all"). "New · Discovered by you" badge if it is the first pull in the league. Duplicate → "+N dust" shown on the card.
3. **Collection**: owned / existing counter, filters by member (photo author) and by rarity, virtualized grid, undiscovered cards as a "???" silhouette, "foil" pip if the foil copy is owned.
4. **Card detail**: large card with a holo effect driven by phone tilt (gyroscope, iOS permission requested on a gesture) or the finger; rarity, variant (foil), author, capture date, discoverer, number of copies in the league; reactions (3 types); actions "Recycle (+N dust)" and, for a card not owned, "Craft (N dust)"; for an owned normal copy, "Upgrade to foil (N dust)".
5. **Add photos**: multiple selection from the gallery or the camera, for each photo: title (required, ≤ 40 characters), people tagged among the members, estimated rarity shown, "GPS location removed" notice. "Create N cards" button.
6. **Profile**: username, avatar (initials), passkey management, password change, leagues, logout.
7. **League admin**: members (role, remove), invitation links (create, revoke), generate a reset code for a member, cards (hide, delete, pin a rarity, validate a photo's date, mark as "event" = Mythic), settings (rarity weights, booster cadence, upload quota).

Screens outside the mockup, to derive from the same visual language: login / signup, join a league, profile, admin.

## 5. Game rules

### 5.1 Card rarity

Tiers: Common, Uncommon, Rare, Epic, Legendary (computed); **Mythic** (admin only, capped at 3 per league).

**Signals**, each converted to a percentile rank within the league (0..1):
- `uploader_scarcity`: the fewer active photos the author has, the rarer.
- `photo_age`: `log1p(years since the EXIF capture date)`. **Capped at 0.5** until an admin has validated the date (an EXIF date can be faked). Photo without an EXIF date = neutral signal.
- `reactions`: Bayesian average of the members' reactions (no reaction on one's own cards).

`score = Σ weight × signal / Σ weight`. Weights adjustable by the league admin (default 1 / 1 / 1), stored as JSON validated by Zod.

**Quota-based assignment** over active cards sorted by score: 45 % Common, 25 % Uncommon, 15 % Rare, 10 % Epic, 5 % Legendary.
- **Hysteresis**: a card only changes tier if it crosses the boundary by more than 2 percentile points.
- **Cold start** (fewer than 20 cards): fixed thresholds on the score, no computed Legendary below 15 cards.
- **Precedence**: rarity pinned by the admin / Mythic > admin min/max bounds > computation. Every override is logged.
- **Recompute**: provisional at upload, full every night and on every settings change. Changes are historized.
- **New card**: out of boosters for 12 h (provisional), so an admin has time to react; the author receives a copy immediately.

### 5.2 Copies

A copy freezes, at pull time, the card's tier (`tier_at_mint`) and its variant (`normal` or `foil`). If the card changes tier afterwards, the copy keeps its original tier. Unlimited copies, no serial number. Each card has a sequential number within the league ("#047").

### 5.3 Boosters

- **Cadence (adjustable per league)**: default 1 booster every 4 h, max stock 6, 2 boosters gifted on joining the league. No scheduled job: the stock is computed from the last computation and the current time.
- **5 cards**: 3 Common/Uncommon slots (80/20), 1 Uncommon+ slot (70 U / 30 R), 1 Rare+ slot (72 R / 20 E / 7 L / 1 M).
- **Pulling a card within a tier**: first pull **an author** uniformly among those who have cards of that tier, then one of their cards. Someone who posts 500 photos does not drown the league. If a tier is empty, fall back to the tier below.
- **Pity**: Epic or better guaranteed after 10 boosters without one; +1 % Legendary chance per booster after 25 without a Legendary.
- **Foil**: 1 copy in 15, all rarities.
- **Fairness and audit**: 100 % server-side pull, in a single transaction, cryptographic random seed recorded (with the pull-table version) so a booster can be replayed. Idempotent opening: a double click does not consume two boosters. The client only plays the animation afterwards.
- You can pull your own cards.
- **Upload quota**: per member and per day (default 10 photos), adjustable by the admin.

### 5.4 Dust

- A member owns **at most one normal copy and one foil copy per card**. A pulled duplicate is **automatically converted** to dust. If the duplicate has a higher `tier_at_mint` than the owned copy, it replaces it and the old one is converted.
- **Every dust value is computed from the copy's `tier_at_mint`** (recycling, duplicate conversion, compensation), never from the current tier. Crafting and foil costs are computed from the card's current tier. Values: Common 5, Uncommon 10, Rare 25, Epic 100, Legendary 400, Mythic 1000, ×2 if foil.
- Recycling an owned copy yields the same value.
- **Crafting** a card not owned costs 4× its value (Common 20 … Legendary 1600). Mythic cannot be crafted.
- **Upgrading to foil** an owned copy costs 2× its value.

### 5.5 Discovery and credits

"Photo by X" on every card. "Discovered by Y" = first member (other than the author) to pull it in the league, frozen for life.

### 5.6 Privacy and image rights

- EXIF read server-side for the capture date, then **stripped** from all stored variants. GPS is never kept.
- Tagging the people in the photo. A tagged member can **withdraw a card they appear in**: it disappears from the league and from collections; owners receive the dust value.
- **Card disappearance** (withdrawal by a tagged member, deletion by an admin, member removed from the league, account deleted): the card and its copies disappear from all collections, each owner is compensated in dust (value of their copy), the files are actually deleted from the bucket. The "Discovered by" credit of a deleted account becomes "former member".
- **Hiding by an admin**: temporary and reversible, the card leaves boosters and is displayed blurred "hidden" in collections, without compensation.
- **Client cache**: on each sync, the app receives the list of withdrawn cards and the service worker purges their images and IndexedDB entries. Signed URLs expire within 48 h at most.
- Bucket region: EU.

## 6. Architecture (decided)

```
pnpm monorepo (workspaces) — strict TypeScript everywhere
apps/web      Vite + React 19 + TanStack Router/Query/Virtual + Tailwind 4 + Motion + Serwist (PWA)
apps/api      Fastify 5 + Zod + Better Auth + Drizzle; also serves the web build in prod (@fastify/static)
apps/worker   pg-boss + sharp: image processing, rarity recompute
packages/shared   shared Zod schemas, types, pure game rules (rarity, pulls, dust)
packages/db       Drizzle schema, migrations, client
```

Railway: `api` service (serves the API + the SPA), `worker` service, PostgreSQL, Bucket. No Redis (pg-boss on Postgres is enough at this scale).

**Pure business logic**: the rarity engine, the booster pull (with an injectable random source), the dust economy and the booster stock computation live in `packages/shared/domain`, with no I/O at all. These are the only modules covered by unit tests (see 6.5).

### 6.1 Images

1. **Client**: resize to 2048 px max and convert to JPEG/WebP via canvas (HEIC decoded natively on iPhone), which also strips EXIF client-side. **The EXIF date is read client-side before conversion and sent with the upload request**; the server treats it as untrusted (age-signal cap).
2. `POST /uploads` → presigned URL (POST with `content-length-range`, max 15 MB), key `incoming/{userId}/{uuid}`.
3. Direct browser → bucket upload, then `POST /uploads/:id/complete`.
4. **Worker**: real type check (magic bytes), metadata stripping, 256 / 768 / 1600 px variants in AVIF + WebP, thumbhash, dominant color, perceptual fingerprint (duplicate photos rejected), then deletion of the `incoming/` original.
5. Variants stored under **immutable keys based on the content hash**, with `Cache-Control: public, max-age=31536000, immutable`.

**Signed URLs and caching**: the API returns **deterministic** presigned GET URLs (signing date aligned to a 24 h window), hence identical during the window and cacheable by the browser. The service worker caches images by object key **ignoring the signature parameters**, so they stay available offline and after re-signing. No image proxy: the browser downloads directly from the bucket (free egress). URLs are only issued to league members.

**Risk to clear first** (throwaway prototype before everything else): presigned upload URL to the Railway bucket, bucket CORS configuration, EU region, and actual stability of signed URLs over a window.

**Allowed fallbacks if the prototype fails**, in this order: (1) presigned PUT instead of POST, size checked afterwards by the worker; (2) if CORS blocks the direct upload, streaming upload through the API (acceptable at this scale), image reads staying direct from the bucket; (3) if signed GET URLs or the EU region are a problem, Cloudflare R2 (same S3 API) instead of the Railway bucket.

### 6.2 PWA and performance

- Serwist service worker: shell precached, images CacheFirst (500 entries, 30 days), API reads stale-while-revalidate, never any cache on booster opening.
- Collection persisted in IndexedDB (TanStack Query persister), `navigator.storage.persist()`.
- Virtualized grid, fixed card ratio (63:88), AVIF/WebP `srcset`, thumbhash placeholder, lazy loading.
- Holo effects in CSS (variables driven in `requestAnimationFrame`, not through React state), active only on the foreground card; `prefers-reduced-motion` respected.
- Code splitting of routes and of the opening screen.
- Targets: LCP < 2 s, INP < 200 ms, CLS < 0.05, initial JS < 150 KB gzip.
- iOS: install help banner (no native install event); no Background Sync, so the upload queue is replayed when back online.

### 6.3 Auth and leagues

- Better Auth: username + password and passkey plugins; sessions in the database. Signup **only through a valid invitation link** (no public signup).
- Invitation link: random token, only the hash is stored, expiration and max number of uses, revocable.
- **An account can be in several leagues.** A photo / card belongs to a single league; duplicate photo detection is per league.
- Roles: owner, admin, member. Any logged-in user can create a league (they become its owner).
- Reset code: **only the owner of the first league the member joined** (their "home league", fixed at signup) can generate it (Tristan's decision, to prevent a stranger from creating a league to take over an account). If the home league no longer exists or no longer has an owner, no reset is possible: passkey or password only. Single use, valid 24 h, stored hashed, logged, invalidates all of the member's sessions. The member enters it together with a new password.
- All business requests are scoped by league with a membership check. Rate limiting on login, reset, invitations. CSRF protection on mutations.

### 6.4 Data (outline, details left to the builder)

users (with home league), sessions/passkeys (Better Auth), leagues (JSON settings), league_members (role), invitations, password_reset_codes, media (keys, variants, thumbhash, capture date, date validated yes/no, fingerprint), cards (title, author, current tier, tier source, admin bounds, score, provisional, number, status), card_tags, card_rarity_history, card_copies (owner, frozen tier, variant), booster_openings (seed, versions, pity state before), booster_pulls, member_wallets (dust, pity counters, booster stock), reactions, audit_log.

### 6.5 Code quality and organization (Tristan's priority)

Clean code and code order come before the quantity of tests.

**Strict separation of responsibilities, no business logic outside its layer:**
- `packages/shared/domain`: pure game rules (rarity, pulls, dust, booster stock). No dependency on Fastify, Drizzle, React or the network.
- `apps/api`, organized **by feature** (`features/leagues`, `features/cards`, `features/boosters`, `features/uploads`, `features/auth`…), each feature split into:
  - `*.routes.ts`: HTTP only (Zod input/output schema, service call, response code). No business rule.
  - `*.service.ts`: use cases. Orchestrates domain + repository + transactions. No SQL, no HTTP object.
  - `*.repository.ts`: database access through Drizzle only. No business rule.
- `apps/worker`: thin jobs calling the same services / the domain, never duplicated logic.
- `apps/web`, organized by feature: purely presentational components, hooks for data (TanStack Query), no game rule client-side (the client displays what the server decided).
- **No comments in the code**, except basic JSDoc on public functions. **Everything in English**: code, README, commit messages.
- Short files (200-400 lines), explicit naming, immutability, typed errors, no `any`, Zod at every boundary (API, env, settings), pino logger (no `console.log`).
- Tooling: ESLint (with import-boundary rules between layers) + Prettier, strict TS (`noUncheckedIndexedAccess`).

**Tests, only what is needed**: a few targeted Vitest unit tests **only** on `packages/shared/domain` (pull and pity, tier assignment, dust, booster stock). No exhaustive test suite, **no CI/CD test pipeline**. Flows are validated through manual and E2E tests in the browser before each delivery.

Local development: Postgres + MinIO (local S3) in Docker Compose; dev servers managed through Portly.

## Addendum — Plan 0 results (2026-11-07)

Spike run on the final Railway project `storix`, bucket `storix-media` (region ams, EU). Endpoint `https://t3.storageapi.dev`, SDK region `auto`, virtual-hosted style (`forcePathStyle: false`). The real bucket name is the one returned by `railway bucket credentials` (it differs from `storix-media`). Bucket CORS kept: origins `http://localhost:5180` and `https://storix.tristanhourtoulle.fr`, methods GET/PUT/POST/HEAD, headers `*`, expose `ETag`, max-age 3600.

**Findings**
- Presigned **POST** with `content-length-range` and an exact `Content-Type` condition: PASS (oversize → 400 `EntityTooLarge`, wrong type → 403); CORS on the POST response is OK.
- `Cache-Control` must be sent as a form field with an `eq $Cache-Control` condition, otherwise stored objects get an empty `Cache-Control`.
- Presigned PUT: works, but `Content-Type` is not enforced and the PUT response has no `Access-Control-Allow-Origin`, so it is unusable from a browser `fetch`. Rejected.
- Presigned GET with `signingDate` at the 00:00 UTC window start and `expiresIn` 172800: byte-identical URLs, 200, no redirect. Max `expiresIn` is 604800 (SigV4 limit). `Cache-Control` set at write time and `ETag` are returned on GET.
- Bucket GET responses carry NO `Access-Control-Allow-Origin`: `<img>` works, but a service worker `fetch` gets opaque responses (status 0), which Chrome pads (~7 MB each) against the storage quota, making the 500-entry image cache of 6.2 unrealistic with direct bucket reads.
- Presigned HEAD needs its own signature (HEAD on a GET URL → 403).

**Decisions (replace the corresponding parts of 6.1 and 6.2)**
- Upload: presigned POST with `content-length-range` (max 15 MB) + exact `Content-Type` + `Cache-Control` form field (fallback 1 of 6.1 is not needed; PUT rejected).
- Reads: **the API serves media same-origin** at `GET /media/{windowStart}/{hmac}/{objectKey}`, where `hmac` = HMAC-SHA256 over `windowStart` + `objectKey` with a server secret, 24 h windows, current and previous window accepted. The API validates, streams from the bucket and responds `Cache-Control: public, max-age=<remaining window>, immutable` with no `Set-Cookie`. This replaces "no image proxy / direct bucket GET" from 6.1.
- The free **Railway CDN** is enabled on the api service (`railway cdn enable`): cache hits incur no egress, it honors `max-age`/`s-maxage`, cache key = method + host + path + full query, requests with `Authorization` bypass it, cookies are not in the key, responses with `Set-Cookie`, `private` or `no-store` are not cached, 512 MB max. Purge on deploy for static assets only. Egress is paid only on CDN misses (about one per image per window per edge), negligible at this scale.
- Same origin means no CORS on media, non-opaque service worker responses, and a service worker cache key that strips `{windowStart}/{hmac}`.
- **Cloudflare R2 rejected**: the `tristanhourtoulle.fr` DNS is on Hostinger, an R2 custom domain needs the zone on Cloudflare, R2 needs a payment method on file and wrangler needs an interactive login; Tristan wants free and doable without him.
- To verify in Plan 2: `x-cache: HIT` on the media route, and no `Set-Cookie` leaking from Better Auth on that route.
